# 布谷鸟过滤器（Cuckoo Filter）深度原理讲解

>
> 论文原文：*Cuckoo Filter: Practically Better Than Bloom*（2014）
> 定位：**支持删除、低空间开销、可控制误判率的近似成员过滤器**，弥补标准布隆过滤器不能删除、查询开销随 bit 数组变大上升的短板；Redisson 实现就是基于这套论文思路。

先一句话核心概括：

>
> 布谷鸟过滤器不存原始元素，只存元素的**指纹 fingerprint**；每个元素有**两个候选桶位置**；两个桶只要有一个有空位就放进去；都满了就随机踢出一个指纹，把被踢的指纹重新找位置，循环踢换（布谷鸟踢）；踢换次数超限就判定过滤器饱和、插入失败。

---

## 一、先对比布隆，建立认知

布隆：多个 hash 置 bit，**无删除、只能 add，不能精准删单个元素**；查询是 O (k)，k 是 hash 函数数量。
布谷鸟：
✅ 支持**单个元素删除**（这是最大卖点）
✅ 查询 O (1)，只查最多 2 个桶
✅ 空间效率和布隆接近，甚至在低误判场景更优
❌ 有插入失败概率（踢换环路卡住），不是无限写入
❌ 同样有假阳性（存在误判：明明不在，判定在），**没有假阴性**（元素在里面一定能查到）

>
> 重要前提：所有近似过滤器共性：`contains(x)=true` 只是 “大概率存在”；`contains(x)=false` 一定不存在。

---

## 二、核心基础结构：桶 Bucket + 指纹 Fingerprint

### 1. Fingerprint 指纹

对元素 `x` 计算一个短哈希值，截取固定 bit 长度作为指纹 `f`。

- 不是完整 hash，很短：比如 8bit、12bit、16bit；**误判率由指纹长度决定**
- 指纹越长，误判率越低；内存占用越高

>
> 论文里：指纹长度 `f_bits` 是控制误判率的核心，**reserve 里那四个参数不控制指纹长度**（Redisson 底层写死）

### 2. Bucket 桶

一个桶是一个固定大小的数组，桶内存放多条指纹。
也就是你刚才看到的 `bucketSize`：一个桶最多容纳多少个指纹。
论文经典配置：`bucketSize = 4`

- bucketSize=4：综合最优，插入成功率高、空间利用率高
- bucketSize=2：省内存，但很容易踢换失败，负载上限低
- bucketSize=8：不容易踢换失败，但是单桶内存变大，空间利用率下降

整个布谷鸟过滤器就是一个大桶数组：`Bucket[] buckets`，桶数量记为 `m`。

>
> 桶数组长度 m，是 reserve 时根据 capacity 和 bucketSize 算出来的：
>
>
> \(m \approx \lceil \frac{capacity}{bucketSize} \rceil\)

---

## 三、双位置哈希公式（布谷鸟最核心公式）

给定元素 x：

1. 计算哈希得到指纹 `f = fingerprint(x)`
2. 第一个桶索引：\(i_1 = hash(x) \bmod m\)
3. 第二个桶索引：\(i_2 = i_1 \oplus hash(f) \bmod m\)

👉 重点：\(i_2\) 不是直接对 x 做第二个哈希，而是 **i1 和指纹 f 的哈希做异或**！
这个设计非常巧妙：

\(i_1 = i_2 \oplus hash(f)\)
**对称性！**

>
> 指纹 f 同时存在 i1 和 i2 的候选集合里：
> 如果 f 在 i1，它的另一个候选位置就是 i2；
> 如果 f 在 i2，它的另一个候选位置就是 i1。

这是**布谷鸟过滤器支持删除的根本前提**！

>
> 删除的时候：我们只知道指纹 f，不知道原始 x。
> 我们只需要去 i1、i2 两个桶里找有没有 f，找到就删掉；
> 如果没有这个异或对称关系，拿到指纹算不出第二个桶，删除就做不到。

>
> ⚠️ 坑点：不同元素，有可能算出相同指纹 + 相同一对桶，这就是冲突，也是误判来源。

### 负载因子 Load Factor

\(\text{load} = \frac{\text{已存储指纹总数}}{m \times bucketSize}\)
负载因子越高，桶越满，插入越容易踢换失败。
论文结论（bucketSize=4）：理论安全负载上限约 **0.95**，也就是 95%。
超过之后，踢换很容易陷入循环，插入失败概率陡增。

>
> 布隆过滤器一般负载到 0.5 左右就已经达到目标误判率；布谷鸟可以扛更高负载，这是优势。

---

## 四、插入流程（Cuckoo Kick 布谷鸟踢换）

输入元素 x：

1. 算出指纹 f、候选桶 i1、i2
2. 检查 i1 桶有没有空位：有空，直接放入，结束 ✅
3. 否则检查 i2 桶有没有空位：有空，直接放入，结束 ✅
4. **两个桶都满了 → 开始踢换循环**
    - 随机选 i1 /i2 其中一个桶
    - 在选中桶里随机挑一条指纹 `f_old`，把它踢出去（踢出）
    - 把当前 f 放到这个空位
    - 现在需要安置被踢出去的 `f_old`：利用异或公式，算出 `f_old` 的另一个候选桶
    - 回到步骤判断：这个新桶有没有空位；满了就继续踢里面随便一个指纹
    - 循环踢换，直到找到空位
    - 如果迭代次数达到 `maxIterations` 还没找到空位 → **插入失败 false**

>
> `maxIterations` 就是你代码里的参数：限制最多踢多少次。
> 踢换本质是链式搬家；运气差会形成环路，无限踢，所以必须有上限终止。

#### 踢换过程举例

f 要进 i1,i2，都满了

- 踢 i1 里的 fa，f 占坑
- fa 的另一个位置是 ia，ia 满 → 踢 ib，fa 占坑
- ib 的另一个位置是 ibb，满 → 继续踢
- …… 迭代到上限失败

>
> 为什么随机踢桶内指纹？确定性踢法容易固定环路，随机可以打破环路，提升成功率。

---

## 五、查询流程（非常轻量 O (1)）

查询元素 x 是否存在：

1. 算指纹 f，i1，i2
2. 去 i1 桶遍历里面所有指纹，看是否等于 f；找到返回 true
3. i1 没有，去 i2 桶遍历；找到返回 true
4. 两个桶都没有 → 返回 false

- 只访问两个桶；每个桶最多 bucketSize 次比对；bucketSize=4 最多对比 8 次，极快
- 误判场景：另一个完全不同的元素 y，刚好指纹也是 f，并且落在 i1/i2 其中一个桶里；此时明明 x 没存，查询返回 true → 假阳性。

>
> 指纹越长，这种碰撞概率越低。

---

## 六、删除流程（布谷鸟区别于布隆的王牌）

删除元素 x：

1. 计算指纹 f、i1、i2
2. 遍历 i1 桶，找到匹配 f 的指纹，删除一条，返回成功
3. i1 没有，遍历 i2 桶，找到匹配 f 的指纹，删除一条，返回成功
4. 都没有 → 删除失败

⚠️ **重要限制：布谷鸟是计数删除吗？不是！**
标准论文布谷鸟过滤器是**单实例指纹**：

>
> 如果同一个元素 `x` add 多次，就会存入多条相同指纹 f；
> delete (x) 只会删掉**其中一条**；多次 add 需要对应多次 delete。
> 它等价于一个简单计数器，但很容易溢出、混淆。
> 工业上两种做法：
>
>
> 1. 不允许重复插入同一个元素（业务层去重），delete 语义干净
> 2. 变种计数布谷鸟（每个槽带上小计数器），Redisson 原生版本没有做计数。

>
> 风险：误删！
> 极端情况：两个不同元素 x、y 指纹相同、共享一对桶；删 x 时有可能删掉 y 的指纹。
> 这个概率等于误判概率，指纹越长风险越低。业务要知晓这个理论风险。

## 七、扩容机制（对应你代码里 expansion 参数）

原生论文布谷鸟过滤器**没有自动扩容**，是固定桶数组大小，满了就插入失败。
expansion 是 Redisson 在 Redis 之上封装出来的能力：
当插入持续失败，判定当前过滤器接近饱和（负载过高）：

1. 创建一个新的、更大的布谷鸟过滤器，容量 = oldCapacity × expansion
2. 遍历旧过滤器里**所有指纹**，逐个重新插入新过滤器（rehash + 重新踢换安置）
3. 切换读写到新过滤器，旧的清理

👉 扩容痛点：

- **重量级操作**：要把 Redis 里整个桶数组全部读出来、迁移；大过滤器扩容会有明显 CPU、带宽抖动
- 迁移过程中，存在短暂双写或者数据不一致窗口，Redisson 做了封装屏蔽，但成本客观
  所以业务最佳实践：**优先评估好容量，尽量少依赖自动扩容**，也就是提前 reserve。

## 八、误判率公式（定性理解）

论文给出近似误判率：

\(P_{fp} \approx 1 - (1 - \frac{1}{2^{f_{bits}}})^{2\times bucketSize}\)

- \(f_{bits}\)：指纹比特长度
- bucketSize：桶大小

举例：
bucketSize=4，指纹 12bit：\(2^{12}=4096\)，误判率大概千分之几级别；
指纹 16bit：误判率降到万分之一以下。
✅ 再次强调：**reserve 的入参改不了指纹长度，改不了基础误判率！**

## 九、常见误区澄清

### 误区 1：布谷鸟可以无限插入

❌ 错。负载逼近上限后，踢换环路概率暴涨，插入失败；要么扩容，要么拒绝写入。

### 误区 2：删除是精准安全的

❌ 有极小概率误删，和误判同源，指纹碰撞；指纹越长越安全。

### 误区 3：i2 是第二个独立哈希函数算出来的

❌ 核心是异或对称，i2 = i1 ⊕ hash (f)，这是为删除服务的关键设计。

### 误区 4：bucketSize 越大误判率越低

❌ 误判率主要看指纹长度；bucketSize 影响的是**最大负载和插入成功率**。

## 十、Redisson CuckooFilter 和论文原版差异梳理

1. 增加了 reserve 预创建接口（原版是懒初始化）
2. 增加 expansion 自动扩容因子（论文无）
3. 指纹长度底层固定，没有开放参数配置
4. 底层存储在 Redis，桶数组序列化放到 Redis 结构，不是内存数组；所以踢换一次就会产生 Redis 读写开销（这一点和单机内存版布谷鸟性能差距巨大！）

>
> 重点提醒：Redis 上的布谷鸟过滤器，**踢换是多次网络 IO**，maxIterations 设很大，流量上来直接打爆 Redis。这也是为什么一般固定 500。
